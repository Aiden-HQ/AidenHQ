# AidenHQ MCP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An owner adds `https://<board>/mcp` to their own Claude, signs in once, and runs the whole instance from it.

**Architecture:**
- The kernel's Better Auth gains an OAuth provider plugin on the admin listener (the authorization server and issuer).
- The board serves a stateless Streamable HTTP MCP at `/mcp`: 14 tools that call the board's own route handlers in
  process, under its request context.
- Bearers are checked by a kernel route.
- Card decisions go through a bearer-authenticated kernel route into the existing `decideCard`.
- `channel-operator` is removed.

**Tech Stack:**
- TypeScript on Node 24.
- `better-auth` 1.7.21 plus its OAuth provider plugin.
- `@modelcontextprotocol/sdk` 1.32.x, the version `modules/apps-platform/apps-mcp` already uses, pinned exactly.
- `node:test` in the kernel, vitest in the board.

**Spec:** `docs/superpowers/specs/2026-11-20-owner-mcp-design.md`. Executors read it first.

## Global Constraints

- Supply chain:
  - every new dependency is pinned exactly and published at least 7 days ago; pick it with
    `scripts/supply-chain/best-version.mjs`;
  - state the release date of each pin in the commit body;
  - `@better-auth/oauth-provider` must match `better-auth` 1.7.21 (published 2026-11-11).
- Work in your own worktree from `origin/main`. Never touch `~/Development/agent-manager`'s checkout.
- Each PR title is a Conventional Commit. The body says why. Squash-merge. Never push to main.
- Tests stay minimal: the end-to-end round trips named below, nothing for obvious code.
- The kernel admin listener's new unauthenticated routes are exactly these:
  - `GET /.well-known/oauth-authorization-server`
  - `GET /oauth/authorize`
  - `POST /oauth/token`
  - `POST /oauth/register`
  - `POST /oauth/revoke`
  
  Every other route keeps its current gate.
- Token lifetimes: access token 1 hour, audience `<board>/mcp`; refresh token sliding 30 days; PKCE S256 only.
- Only a ready admin (TOTP enrolled, not disabled; `accountSession` rules) may authorize, introspect or decide.
- Writes made over MCP run as `account:<id>` with `via: "mcp"`. A stale reject is stamped `stale:account:<id>`, rejects
  only.
- `ask` waits for `wait_seconds`: default 20, maximum 50.
- Board changes: run `npx tsc -p tsconfig.build.json --noEmit` as well as vitest.
- Kernel changes to `writes.ts`: a passing reviewer-eval receipt (CLAUDE.md, "Build and test").

## Review Focus

1. **Revoke takes effect on the next write.** After a grant is revoked or the account is disabled, a write on a token
   that is still unexpired is refused, even inside the board's 5 s read cache. Tested in Task 3.
2. **A card changed after it was read.** `decide` with an old digest returns that card's conflict, and the other cards
   in the same call still succeed. Tested in Task 2 and Task 3.
3. **Cross-origin browser requests to `/mcp`.** A request with a foreign `Origin` header is refused (DNS-rebinding and
   CSRF class); a request with no Origin and a bearer is accepted. Tested in Task 3.
4. **A token whose audience is another resource** (for example one minted for a different board URL) is refused by
   `/v1/auth/mcp`. Tested in Task 1.
5. **`ask` on a slow agent** returns the chat id within `wait_seconds` and never holds the request past 50 s. Tested in
   Task 3.

### Task 1: Kernel authorization server (spike first)

**Files:**
- Modify: `kernel/package.json`, `kernel/package-lock.json` (add the OAuth provider plugin, exact pin)
- Modify: `kernel/src/auth-rules.ts` (register the plugin; the admin listener's `EXPOSED` set gains the OAuth endpoints)
- Modify: `kernel/src/admin.ts` (route the five OAuth paths before the session gate; one consent page)
- Modify: `kernel/src/accounts.ts` (grant check, list and revoke)
- Modify: `kernel/src/auth-api.ts` (`POST /v1/auth/mcp`, `POST /v1/auth/mcp/grants`, `POST /v1/auth/mcp/revoke`; all
  with the board key)
- Test: `kernel/test/mcp-oauth.test.ts`

**Interfaces:**
- Produces:
  - `accounts.mcpGrant(token: string, resource: string): Promise<{ account: Account; client: string; expires: string } | null>`.
    It returns null for an expired, revoked or wrong-audience token, or for an account that is not a ready admin.
  - `accounts.mcpGrants(accountId: string): Promise<Array<{ id: string; client: string; lastUsed: string | null }>>`
  - `accounts.revokeMcpGrant(accountId: string, grantId: string): Promise<void>`
  - Disabling or resetting an account calls the same revoke for all of that account's grants.
- HTTP (board key):
  - `POST /v1/auth/mcp {token, resource}` → `{ account: {id,email,name,role,owner}, client, expires }` or 401.
  - `POST /v1/auth/mcp/grants {account}` → `{ grants }`.
  - `POST /v1/auth/mcp/revoke {account, grant}` → `{ ok: true }`.

  - audience binding;
  - revocation by account;

### Task 2: Kernel decide over a bearer, and stale rejects by an account

**Files:**
- Modify: `kernel/src/writes.ts` (the `decide` stamp check: also admit `stale:account:<id>`, and only with
  `decision: "reject"`)
- Modify: `kernel/src/auth-api.ts` (`POST /v1/owner/decide`, board key plus the MCP bearer)
- Test: `kernel/test/mcp-oauth.test.ts` (extend)

**Interfaces:**
- Consumes: `accounts.mcpGrant` (Task 1) and the existing `cards.decideCard(id, digest, decision, by, via, reason)`.
- Produces:
  - HTTP `POST /v1/owner/decide {token, resource, cards: [{id, digest, decision: "approve"|"reject", reason?, stale?}]}`
    → `{ outcomes: [{ id, ok: boolean, state?: string, identifier?: string, error?: string }] }`.
  - `by` is derived from the grant (`account:<id>`, or `stale:account:<id>`). It is never read from the body. `via` is
    `"mcp"`.

- [ ] **Step 1: Write the failing test** `owner decide over MCP`, using two pending fixture cards:
  - one with the right digest and one with an old digest give outcomes `[ok: true, ok: false with a "changed since you
    read it" error]`;
  - `stale: true` with `decision: "approve"` is refused;
  - `stale: true` on a reject records `stale:account:<id>`, and the card's state counts as stale, not a veto;
  - a revoked token gets 401 before any card is touched.
- [ ] **Step 2: Run it.** Expected: FAIL.
- [ ] **Step 3: Implement** the route and the stamp check. Each card is decided independently, so one failure never
  aborts the rest.
- [ ] **Step 4: Run it.** The test passes. Then `npm test && npm run typecheck`. Then run the reviewer eval
  (`node modules/ai-reviewer/scripts/reviewer-eval.mjs`, with the key from the eval vault entry, run on the VM as
  CLAUDE.local.md describes). It must reach 95% or more, and every miss must be a false block.
- [ ] **Step 5: Commit**, in the same PR as Task 1 or stacked on it:
  `feat(kernel): an owner's MCP client decides cards as the account`.

### Task 3: The board's `/mcp`

**Files:**
- Modify: `services/board/package.json`, `services/board/package-lock.json` (`@modelcontextprotocol/sdk`, the exact
  version apps-mcp resolves)
- Create: `services/board/src/mcp.ts` (server, instructions, the 14 tools)
- Create: `services/board/src/mcp-auth.ts` (bearer check through the kernel, plus the protected-resource metadata)
- Modify: `services/board/src/app.ts`:
  - route `/mcp` and `GET /.well-known/oauth-protected-resource` before `checkRequest` and `accountGate`;
  - add `via` to the `perRequest` store (`AsyncLocalStorage<{ session; via?: "mcp" }>`);
  - expose an in-process `callRoute(method, path, body, session)`.
- Modify: `services/board/src/kernel-auth.ts` (`mcpGrant(token)`, `decide(token, cards)`, `grants(account)`,
  `revoke(account, grant)` as clients of Task 1 and Task 2)
- Modify: the board's account page (`services/board/web/src/...`, the page that lists the admin's sessions or account)
  plus two account routes: list MCP clients and Revoke.
- Test: `services/board/test/mcp.test.ts`

**Interfaces:**
- Consumes: the Task 1 and Task 2 HTTP routes.
- Produces:
  - `createMcp(d: { callRoute; kernel; boardUrl }): (req, res, session) => Promise<void>`
  - `callRoute(method: string, path: string, body: unknown, session: BoardSession, via: "mcp"): Promise<unknown>`. It
    finds the route in the same `routes` table `routeApi` uses and runs it inside `perRequest.run({ session, via })`.
- Tool names, hints and behaviour are exactly the spec's table:
  - read: `status`, `tasks`, `get_task`, `approvals`, `fleet`, `modules`, `connect`, `apps`, `costs`;
  - write: `ask`, `create_task`, `update_task`, `decide`, `change_settings`.
  
  Each has an `outputSchema` and returns `structuredContent` plus one short text line. Lists take `cursor` and return
  `next_cursor`. Agent-authored and external text is fenced with the shared `fence`.
- Server `instructions`: start with `status`; use `ask` for anything that needs judgment or work; use `change_settings`
  for configuration; links in results open the board for a human.
- Which route handlers each tool composes is the builder's call (spec, "Left to the builder"). Use the route inventory
  in `app.ts`:
  - `GET /api/needs-you`, `GET /api/approvals` and `/explain`, `POST /api/chats`, `GET /api/chats/:id`,
    `POST /api/issues` and `/comments`, the move, schedule and stop routes, `GET /api/agents*`, `GET /api/modules*`,
    `POST /api/settings/change`, `GET /api/sign-ins/:id`, `GET /api/apps`, `GET /api/costs/*`.
  
  A tool that would need more than a small extraction is cut and listed in the PR body.

- [ ] **Step 1: Write the failing test** `mcp end to end`, against a fake kernel in `test/kernel.ts` that answers
  `/v1/auth/mcp` and `/v1/owner/decide`:

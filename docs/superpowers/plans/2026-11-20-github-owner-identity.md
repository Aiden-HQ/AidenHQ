# GitHub as the Owner Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** AidenHQ acts on GitHub only as the owner, through the one device sign-in. The GitHub App, its key, its setup page
and the kernel's token broker are deleted.

**Architecture:**
- `github-mcp` and the code host (`modules/github/service`) become one container and one Node process. Both source trees
  stay where they are.
- The process holds the owner's token. It runs one GitHub client with one rate limiter and typed errors.
- Other modules no longer get tokens. They get typed code host operations through the kernel's `/v1/codehost/:op`.
- Authority moves into AidenHQ's own records:
  - successful write outcomes carry GitHub object refs, and one kernel lookup answers "is this ours";
  - the owner's word to build a feature is the owner's own message in AidenHQ, checked in kernel code.

**Tech Stack:** TypeScript on Node 24. `node:test` in the kernel, scripts, `modules/github` and `services/computer`; vitest
in github-mcp, apps-mcp and the board. No new dependencies.

**Spec:** `docs/superpowers/specs/2026-11-20-github-owner-identity-design.md` (approved 2026-11-20). Every executor reads
it first. Section numbers below (§n) are the spec's.

## Global Constraints

- Follow the product `CLAUDE.md` "Conventions" section in full:
  - TypeScript, one way, no fallbacks;
  - delete the old path in the same PR;
  - minimal tests: a few end-to-end tests per lane, no unit-test bloat. Deleting App tests is expected.
- Owner-fixed format (2026-11-20): the trailer names the agent (e.g. `Co-authored-by: AidenHQ Engineer <noreply@aidenhq.ai>`), and every posted text links to https://aidenhq.ai. Attribution markers (flow.ts) match `noreply@aidenhq.ai` and the `https://aidenhq.ai` footer link, not exact names.
- Commit trailer, exactly: `Co-authored-by: AidenHQ <agent name> <noreply@aidenhq.ai>`.
- Text footer, exactly: `🤖 Generated by <agent name> with [AidenHQ](https://aidenhq.ai)`. Use `Caller.name` (`kernel/sdk/src/caller.ts`), or the module's
  name for background writes.
- First-connect scopes, exactly: `repo`, `read:org`, `workflow`, `project`. Add `admin:org` only while the `ci` module is
  enabled.
- Rate-limit reserve: background work pauses while REST or GraphQL `remaining` is below 20% of `limit`.
- Not-connected copy: `GitHub isn't connected`. Every not-connected refusal uses exactly this text, including
  `create_repo` with `github_fleet_org` set.
- The owner's token never leaves the GitHub process. The one exception is the host credential helper, which reads the token
  file (§2). No op returns it and no env carries it to a job, box or other container.
- Never `git stash`. Never `git add -A`. Build in your own worktree from `origin/main`, never in
  `~/Development/Aiden/AidenHQ`.
- Frozen data is not renamed: `modules/ai-reviewer/test/reviewer-cases/*.json`, the fleet-steward eval cases under
  `modules/fleet-steward/test/evals/` and `scripts/lean/parity.json` keep their old tool names. They are recorded history,
  not live grants. Only a case that a test asserts against the live tool list is updated, with a note in the commit body.

## Contracts (every lane builds against these; Task 1 and Task 4 create them)

**GitHub access in the process** (`modules/github/connections/github-mcp/src/client.ts`, Task 1):

```ts
export type Need =
  | { cause: "not_connected" } | { cause: "expired" } | { cause: "scope"; scope: string }
  | { cause: "sso"; org: string; url: string } | { cause: "restricted"; org: string; url: string }
  | { cause: "unreachable"; repo: string } | { cause: "rate_limited"; until: string };
export class GitHubNeed extends Error { need: Need; ownerFixable: boolean }   // ownerFixable: not_connected|expired|scope|sso|restricted
export const needKey = (n: Need) => string;  // "github:<cause>[:<org|scope>]", the notify dedupe_key
export interface GitHubAccess {
  connected(): boolean;
  identity(): Promise<{ login: string; name: string; email: string }>;  // email: <id>+<login>@users.noreply.github.com
  token(): Promise<string>;           // for git children inside this process only (credential env), never returned by any route
  rest(method: string, path: string, body?: unknown, o?: { background?: boolean; accept?: string }): Promise<{ status: number; body: any; headers: Headers }>;
  graphql(query: string, variables: Record<string, unknown>, o?: { background?: boolean }): Promise<any>;
  scopes(): string[];                 // from X-OAuth-Scopes
  status(): GitHubStatus;             // the board card's data (Task 11 renders it)
}
export type GitHubStatus = { login?: string; scopes: string[]; problems: { org: string; cause: "sso" | "restricted"; url: string }[]; rate?: { remaining: number; limit: number; reset: string } };
```

`rest`/`graphql` throw `GitHubNeed` for:
- 401: `expired`, or `not_connected` with no token;
- 403 with `X-GitHub-SSO`: `sso`, with that header's URL;
- 403 "OAuth App access restrictions": `restricted`, with `https://github.com/orgs/<org>/policies/applications`;
- `X-Accepted-OAuth-Scopes` not covered by `scopes()`: `scope`;
- 404 on a repo path: `unreachable`;
- 403/429 rate limit: `rate_limited`.

Any other status returns as is. On an owner-fixable need the process calls the kernel's `POST /v1/notify`
(`kind: "alert"`, `dedupe_key: needKey(n)`, one link) at most once per key per process, with the code host's token (role
`kernel.owner-notice`).

**Kernel ops** (`POST /v1/codehost/:op`, Task 4). `token` is deleted. Grant keys go in `kernel/schemas/codehost.json`:

| op | body | answer | grant key |
|---|---|---|---|
| `snapshot`, `clone` | unchanged | unchanged | `snapshot`, `clone` (unchanged) |
| `bundle` | unchanged (the kernel's own, never a module's) | unchanged | `clone` |
| `fetch` | `{repo, ref: "refs/heads/*" \| "refs/heads/<b>" \| "refs/pull/<n>/head"}` | a git bundle of those refs | `fetch: {repos}` |
| `head` | `{repo, ref: "<branch>"}` | `{sha}` | `fetch` |
| `read` | `{repo, kind: "pr" \| "issue" \| "diff" \| "job" \| "prs", number?, id?}` | grading's PR/issue shape (the queries move from `grading/service/src/github.ts`), diff text, job `{id,name,state,conclusion,run_id,url}`, open PRs `[{number,sha,base,head_repo}]` | `read: {repos}` |
| `comment` | `{repo, number, body, id?}` | `{id}`; the footer is added in the code host | `comment: {repos}` |
| `commit` | `{repo, branch, path, content, parent, message}` | `{sha}`; 409 when `branch` moved off `parent`; owner identity plus trailer | `commit: {repos, paths}` |
| `runner_token` | `{org}` | `{token, expires_at}` (the runner registration token only) | `runner: {orgs}` |

Repo patterns keep today's grammar: `@instance`, `@product`, `@orgs`, `@maintained`, `@agents/<name|*>`, `owner/name`,
`owner/*`, `*/*`. `@agents` resolves to `github_fleet_org` (plus `local` with codehost-local).

**Write outcome objects** (Task 5):
- Executor `execute`/`status` answers and conn.tool results may carry `objects: string[]`. A conn.tool result carries them
  in MCP `structuredContent._aidenhq.objects`. The kernel stores them with the outcome.
- Refs, exactly:
  - `github:<owner>/<repo>#<n>` (an issue or PR);
  - `github:<owner>/<repo>@<sha40>` (a commit);
  - `github:<owner>/<repo>#<n>/comment/<id>`;
  - `github:<owner>/<repo>#<n>/label/<name>`.
- Background writes post facts with `data.objects`. The kernel indexes those too.
- Lookups (role `kernel.work-read`):
  - `GET /v1/objects?ref=<ref>` answers `{ours: boolean, record?: string, at?: string}`;
  - `GET /v1/objects?type=pr&since=<iso>` answers `{refs: string[]}`.

- github-mcp and the code host get it as `GITHUB_FLEET_ORG`.

## Review Focus

- **Disconnected at a bad moment.** The token is revoked while a merge is queued or a push record is approved. Expect the
  merge queue to post `work.waiting` reason `github`, `execute` to answer `running` (held), and both to resume on
  reconnect. Neither fails nor runs twice. Test: Task 2 `held write resumes on reconnect`.
- **Labels work as today (owner, 2026-11-20).** `agent-build` and the fix label added by the owner's login count, as an
  admin collaborator's do today, whether the owner or an agent added them: they give the owner visibility, they are not a
  security boundary. Test: Task 8 `labels by the owner's login trusted, as today`.
- **The owner's token leaking through an op.** Expect no op's answer, header or error text to contain the token. Test: Task 4
  `no op answer carries the token` (the fake token string is absent from every answer body).

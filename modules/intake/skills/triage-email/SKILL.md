# Inbox scan

Two signals, one task per Gmail thread. The `Aiden` label is the owner's explicit "make this a task"; the inbox feed is everything else that arrived, judged by you. Your one Gmail write is `gmail_label` removing `Aiden` from a thread whose task the owner closed, so the label marks open work only.

1. **Labelled:** `gmail_search` `label:Aiden`, `max_results` 50, no `account` (all accounts). Group by `account` and `thread_id`. An account with an `error` or exactly 50 messages has an incomplete list.
2. **Label removed:** `task_list` `label: "email"`, `limit: 200` (the tool's maximum), `task_get` each for its `source:gmail:label:<thread_id>` marker and `Account:` line. A thread absent from step 1 whose account listed completely lost its label: the owner marked it handled, so close the task as skill `owner-triage` says ("Label removed in Gmail: <the task's Link>"), once: a task the owner reopened after such a close (its comments already carry that line) stays open. Otherwise nothing. Incomplete accounts keep their tasks.
3. **Labelled threads become tasks:** `gmail_read_thread` (its `account`), then `task_create`: `marker: source:gmail:label:<thread_id>`, `related_markers: ["source:gmail:<thread_id>"]`, `dedupe_closed: true`, `labels: ["todo", "email"]`, `title` what the owner needs to do ("Read: <topic>" if informational), Reason starting "Labelled `Aiden` in Gmail." A `deduplicated` answer: `task_get` it and read its marker. With the label marker: closed with `auto-closed` means an agent closed it (on evidence, or when the label was removed), so a label back now is the owner asking for it again: reopen it with `task_comment` `reopen: true` ("Labelled `Aiden` again: <link>") and leave the label. Closed without `auto-closed` means the owner finished it, so `gmail_label` (`thread_id`, its `account`, `remove: ["Aiden"]`) and nothing else. With only the inbox marker (`source:gmail:<thread_id>`): open, it stays the thread's task, with one `task_comment` "Labelled `Aiden` in Gmail." if it has none; closed, the owner wants the thread back, so `task_create` again without `related_markers` (a new labelled task).
4. **Inbox:** `gmail_inbox_new` (`limit` 20). Each row is one thread's newest message from any sender since your last scan; newsletters, notifications, mailing lists, auto-replies and no-reply senders are already left out (`dropped` counts them). Skip a thread already handled in step 3. A row with `replied: true` has the owner's own message newest: `task_search` `source:gmail:<thread_id>`; when it finds an open task, `gmail_read_thread` and, if that message answers the ask, close it as skill `owner-triage` says ("Answered in Gmail: <link>"); otherwise leave it and file nothing (a later reply from someone else would be the row instead). Judge each remaining row from its sender, recipients, subject and snippet, and `gmail_read_thread` (its `account`) only for a thread that may need the owner. A thread becomes a task when it is addressed to the owner and needs their own decision, answer, review, approval, signature or access; when the owner promises something concrete in it; or when someone promises the owner something concrete. Everything else is nothing: FYIs, receipts and confirmations, announcements, cold outreach and sales pitches, threads where the owner is only on Cc (`cc_only`) unless they are asked by name, and threads someone else already answered. Pick nothing when torn. `task_create`: `marker: source:gmail:<thread_id>`, `related_markers: ["source:gmail:label:<thread_id>"]`, one label like a Slack task (`needs-response` for an ask of the owner, `todo` for the owner's promise, `waiting-on` for one made to them, titled by what is owed and by whom), `title` `Reply to <person>: <topic>` or the action, Reason one sentence on what is asked or promised. Before filing, look for the same person and ask, and right after, place each new task (skill `owner-triage`).
5. **Both kinds:** `priority` `high` for a deadline today or tomorrow or a blocker, `low` if plainly FYI, else `medium`; `description` your mission's format with `Type: Email`, `Account:`, `From:`, `Subject:`, `Received:` (newest message, ISO 8601 with its UTC offset, e.g. `2026-10-05T13:47Z`), `Link:` (the result's `link`, unchanged). On an open duplicate with a message newer than the task's creation and its last comment (compare times; replies already in the task don't count): a one-sentence `task_comment`, and `task_update` the priority if warranted.
6. Once every inbox thread is decided, `gmail_inbox_ack` with the `cursor` `gmail_inbox_new` returned. When it said `more`, after that ack call `gmail_inbox_new` again and repeat step 4, at most 3 batches a run. An account with an `error` keeps its place for the next scan; say so in your summary.
7. Finish the run with a count line, e.g. "Labelled: 3 threads across 2 accounts (1 new task); inbox: 14 threads, 2 tasks (1 needs-response, 1 waiting-on), 41 automated set aside; closed 1 on a removed label; cleared the label from 1 closed task". `task_finish` on your run task, or, when the run is woken on a task you filed for the owner (this run's own task), that count line as the `task_comment` (plus, when the task is assigned to you, `task_wait` `for: "owner"` with `question: "Nothing left on this task; please close it."`), and `task_finish` there only to close it on its evidence (skill `owner-triage`).
